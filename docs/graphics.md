The game draws through the Xbox's Direct3D 8 library (D3D8, XDK 5659), which is linked into the XBE. Its calls stay in the recompiled code; what answers them is the runtime. Every D3D function the game calls is replaced natively (`recomp/runtime/host/d3d.cpp`) over a Vulkan 1.3 renderer (`recomp/runtime/gfx/`). There is no DirectX anywhere, and the Xbox's GPU (the NV2A) isn't emulated: the replacements see what the game asks for (clear this, draw that mesh with this texture) and do it with Vulkan.

```
lifted game code  →  D3D call  →  replacement (d3d.cpp)  →  renderer (gfx/)  →  Vulkan  →  the GPU
```

## What the game uses

The game's own code (and Rare's libraries) call 90 D3D functions, 1,095 call sites in all (`docs/code-analysis.md`). XbSymbolDatabase names 84 of them by signature; the other six were identified by reading them (`D3DDevice_BlockUntilIdle`, `D3DDevice_CreateSurface2`, `D3DTexture_GetLevelDesc`, `Direct3D_SetPushBufferSize`, D3D's contiguous-memory allocator, and a push-buffer helper at `0x176E00` still to name). `tools/gen/xdk_symbols.py` turns the database's scan into `recomp/runtime/host/xdk_symbols.inc`, which gives the runtime the names of 390 XDK library functions and variables (D3D8, DSOUND, XACT, XAPI, XGraphics). Reports use them: `no replacement for D3D8 D3DDevice_SetTexture (001749E0)`.

The game never reads the D3D device object, so the device is the runtime's. But it does write D3D's state directly: the XDK's `SetRenderState` and `SetTextureStageState` are inline functions, so the game stores render states into `D3D__RenderState` (`0x181B70`), texture-stage states into the table at `0x181970`, and sets bits in the dirty-flags word at `0x181968`, 148 writes in all. Those tables stay in guest memory in the original layout and are the source of truth: the renderer reads them when it draws.

Resources (surfaces, textures, vertex buffers) stay D3D resource headers in guest memory, as the game passes them around and may read their format and size: `Common` (reference count in the low 16 bits, type, the device's internal references), `Data`, `Lock`, `Format`, `Size`, and a surface's `Parent`. Their data stays in guest memory too, where the game writes it; the renderer copies what it draws into Vulkan images when it draws.

**D3D's resource code is lifted** (v0.16.0, `kLiftedD3d` in `recomp/src/main.cpp`): creating textures, surfaces and vertex buffers, surface levels, descriptions and locks, pixel-shader objects and D3D's contiguous allocator, 21 functions. They're computation over the game's own allocator (`0xF7270`), so lifting them makes headers, sizes, pitches and swizzled layouts exactly the original's. What they call that touches the GPU stays native: `D3D_BlockOnResource`, the wait for the GPU to finish with a resource, returns at once (the GPU never holds guest memory here), and `D3DVertexBuffer_Lock2`, which in the original also writes a wait into the command buffer. The lifted code reads a few fields of the device object, which the runtime keeps current in the original layout: the frame buffers (`+0x1A04`, `+0x1A08`, `+0x1A0C`), the render target (`+0x19F4`), the depth buffer (`+0x19F8`) and the multisample type (`+0x195C`).

**Locks return addresses in the kernel's windows onto RAM**: a vertex buffer's `Data | 0x80000000`, a surface's `Data | 0xF0000000` (write-combined). The game writes vertices and pixels through them, so guest RAM is mapped at both (`runtime.md`).

## Vertex shaders

The game has 24 vertex shaders, written in Xbox shader assembly (`vs.1.0` and `xvs.1.1`, a table at `0x4271E4`) and assembled when it starts by XGraphics' `XGAssembleShader`, which is lifted. So the microcode `CreateVertexShader` receives is exactly what the console's would be.

`recomp/runtime/gfx/vsh.*` decodes it: a header word (program type, instruction count), then 128-bit NV2A instructions, each pairing a MAC operation (`mov mul add mad dp3 dph dp4 dst min max slt sge arl`) with an ILU one (`mov rcp rcc rsq expp logp lit`), three operands (A, B, C) from temporaries, inputs or the 192 constants (D3D's c-96…c95), with swizzles, negation and a0.x-relative constants, writing temporaries, an output register (`oPos oD0 oD1 oFog oPts oB0 oB1 oT0`–`oT3`) or a constant. `ADD` reads A and C; the ILU reads C, and writes `r1` whenever the MAC slot holds an operation (the assembler keeps `r1` free for it).

**Checked against the sources:** each of the game's 24 programs disassembles to its source text, after what the assembler itself does: it renames temporaries, writes `sub` as `add` with a negated operand, narrows write masks, expands `m4x4` into four `dp4`, pairs ILU operations with MAC ones, and appends the screen-space transform (`mul oPos.xyz, oPos, c-38` with `rcc r1.x, oPos.w`, then `mad oPos.xyz, oPos, r1.x, c-37`: D3D's reserved viewport constants). `qilin_gfx_tests` checks one of them, as the assembler produced it, against its disassembly. `QILIN_DUMP_VSH=1` prints every program and its declaration as it's created (`=2` adds the raw words).

`CreateVertexShader` builds the shader object as the original does (v0.20.0), with D3D's own helpers, lifted, over the game's allocator: a reference count, flags (`0x10` a program), the instruction count, 16 attribute slots `{stream, offset, format}` filled from the declaration (format `2` is disabled), then the program and the declaration's constant loads in push-buffer form at `+0x114`. The handle is the object's address with bit 0 set, which tells programmable shaders from fixed-function vertex formats (an FVF becomes D3D's fixed-function object at `0x184478`). `SetVertexShader` with a program loads it at slot 0 and selects it, as the original's `LoadVertexShader` and `SelectVertexShader`: the runtime keeps the GPU's 136-slot program memory and 192 constants (`vs_program`, `vs_constants`), filled from the object's push-buffer form and by the `SetVertexShaderConstant*` calls. The renderer decodes the program at the selected slot when it draws and makes it SPIR-V (Drawing, below).

**Pixel shaders** are the NV2A's register combiners: `CreatePixelShader` and `DeletePixelShader` are lifted (they only allocate, copy the game's `D3DPIXELSHADERDEF` and free), so the renderer reads the combiner settings from the original object.

## The renderer

`gfx::Renderer` (`recomp/runtime/gfx/gfx.hpp`) is the only code that touches Vulkan.

- **Vulkan 1.3 core**, loaded at run time through volk: building needs no Vulkan SDK, and a machine without Vulkan gets a message naming what's missing. It uses dynamic rendering and synchronization2 (both core in 1.3), picks a discrete GPU over an integrated one over a software renderer (`--gpu N` chooses), and enables `VK_KHR_portability_subset` where it's offered (MoltenVK).
- **Frame buffers are the renderer's own images**, B8G8R8A8 as the Xbox's A8R8G8B8, plus a D24S8 depth buffer (D32S8 where a GPU has no D24S8, as on Apple GPUs). The D3D back buffer is drawn into; `present` flips, as the Xbox's `Swap` does. Rendering doesn't depend on a window: a frame can be read back, saved (`--dump-frames`) or later scaled to any window size.
- **Clears:** a clear of the whole buffer before anything is drawn becomes the render pass's load operation, which is what tile-based GPUs (Raspberry Pi, Apple) need to run well; other clears are `vkCmdClearAttachments`.
- **The window** (v0.23.0) is SDL3's (`recomp/runtime/platform/window.*`); the renderer stays free of SDL, and the window gives it what a swapchain needs (the surface, the instance extensions, and Vulkan's loader as SDL loaded it, so both use one library). `present` copies the new front buffer into the swapchain, scaled with linear filtering to the largest size that keeps its shape, with black bars around it, then presents: MAILBOX where the GPU has it (least latency, no tearing), FIFO otherwise; the game paces itself through `Swap`'s vblank wait, so the window's refresh rate doesn't change its speed. The swapchain is made again when the window changes size or the driver reports it out of date or suboptimal; a minimised window gets nothing. The window opens at the picture's shape, as large as fits nine tenths of the main display (v0.40.1; before, a whole multiple of 480 lines); F11 or Alt+Enter switch fullscreen; closing it stops the runtime. SDL's events are handled at each `Swap`, on the game's thread (macOS takes events only on the first thread, which is the game's). `--headless`, or no display, runs without a window.
- **Two submissions in flight** (v0.30.0): the CPU records the next submission while the GPU runs the last. Each of two slots has its own command buffer, fence, descriptor pool, 32 MB ring for vertices, indices and uniforms, and acquire semaphore, and keeps what its submission used (staging buffers, destroyed textures) until its fence says the GPU is done; a new submission waits only for the slot's previous one. Reading pixels back (`CopyRects` from a frame buffer into a texture of more levels, a frame-buffer lock, `--dump-frames`) waits for both. Before v0.30.0 every submission waited for the GPU, so the game's thread stood still while the GPU drew. Since v0.30.2 a slot also keeps the descriptor sets its draws wrote, keyed by their textures and samplers (the uniform buffers are dynamic, so their offsets aren't part of the set): a draw with the same textures reuses one, and they go with the pool's reset when the slot is reused. A 300-second run under the validation layer reports nothing.
- **What a draw costs** (v0.31.0), measured on the attract sequence (lavapipe, x86-64): 113 µs of the game's thread per draw before, 25 µs after. The render-target hashing above was 46 µs of it. Textures compared by `memcmp` against their copy instead of hashed: 11 µs to 6 µs, now bound by memory bandwidth (about 40 KB a draw). The renderer sets only the state that changed since the last draw in the command buffer (pipeline, viewport, scissor, cull, depth, stencil, blend constants; forgotten when a command buffer begins and when the present pass binds its own pipeline), and binds the vertex attributes in one call: 16 µs to 10 µs. Vertices are converted a run at a time with the format chosen once, read in place after one bounds check, into buffers kept from the draw before.
- **The vertex arena** (v0.34.0): a 64 MB buffer of vertex data that stays from frame to frame, device-local and written by the CPU where the GPU has such memory (integrated GPUs, Apple's, the Raspberry Pi's, resizable BAR; not the 256 MB window of a discrete GPU without it), else host memory. A draw of 16 vertices or more takes each vertex stream from it: the stream's converted attributes, keyed by the stream's address, stride, vertex count and attribute layout, kept with a copy of the guest bytes they came from. At each draw the bytes are compared with the copy (a `memcmp`, which costs far less than converting and copying the floats); the same, the draw reads the arena; changed, they're converted into new space and the old is freed once the submissions that read it are done. A stream that changes three draws in a row is drawn the old way for 300 swaps, and streams not drawn for 120 swaps leave the arena. **Constant attributes** (an attribute the vertices don't have, which reads the register `SetVertexData*` last wrote) are one vec4 in the ring, bound at the instance rate, instead of the value copied once per vertex. Measured in play (the mansion's first fight, lavapipe): 100 MB a frame through the ring before, 4 MB after (34 MB of it was constant attributes copied per vertex, the rest meshes that didn't change); the game's thread from 43% of a core to 25%. Since v0.41.1 a stream unchanged for 60 swaps is compared at its first draw in a frame and again only after a lock (`BlockOnResource`, `D3DVertexBuffer_Lock2`): the shadows draw the floor again for every character, and comparing at every draw was 30 MB a frame in a fight. `QILIN_NO_VERTEX_CACHE=1` turns both off.
- **The picture and the settings menu** (v0.36.0): `Picture` (the settings' [display]) says how the frame fills the window: whole multiples of its lines, the largest that keeps its shape, or the whole window; at the shape the game draws for (below); sharp (as v0.30.2) or smooth; plain or a CRT television (each frame line lit across its middle and dark at its edges by `scanlines`, the window's columns through red, green and blue stripes by `mask`, brightened back to the frame's average level). The present pass takes them as a second vertex attribute, so a change costs nothing. Vsync on is FIFO; off, MAILBOX, else IMMEDIATE. Anisotropic filtering (up to the device's limit, 16x) applies to the game's linearly minified textures. The settings menu (Dear ImGui, `recomp/runtime/ui/`) draws in the present pass after the frame (`set_overlay`); while it's open the game stands still in `Swap`, the last frame shown again under it (`present_again`), and the time it was open is taken off the game's vblank clock and the sound's.
- **Frame rate and latency** (v0.40.0): the game runs at 30 frames a second as on the console, 60, the display's refresh rate (the default) or unlimited; its time step then comes from the clock (`frame-timing.md`). With vsync and low latency (the default) the swapchain has the fewest images FIFO allows (two at least), so at most one finished frame waits for the display; MAILBOX keeps one more. Unlocked, `Swap` takes the window's next image before returning (`acquire_early`: that waits for the refresh), so the game reads its input for the next frame just after the display took the last, and the frame it draws is shown at the next refresh. A swapchain made again in between hands the early image's semaphore a submission that waits on it, so it's never signalled twice. Acquire semaphores are a pool of their own (v0.42.2), each free again when the submission that waited on it has finished: with the recording slot's own, an image taken early under one slot and presented from the other (a flush in between) left the semaphore's wait queued when its slot next acquired. `QILIN_FPS=1` logs the frame rate and the time step once a second. Every frame over 50 ms is logged (v0.41.2; the player kit's `run.log`) with the game's share of it, the pipelines made for its draws and the textures made or written within that, and presenting's share. F3 (or `performance_overlay`) shows a frame rate counter top left (`ui/frame_times.hpp`, from PunchOutWii--QilinRecomp: the average, the 1% and 0.1% lows over 20 s, the worst frame, a graph), with the target, vsync and the game's time step; the settings menu's pauses aren't counted.
- **Pipeline cache** (v0.31.0): compiled pipelines are kept in `vulkan_pipelines.cache` in the data directory (beside the hard disk's partitions, outside them), loaded at start when its header names this GPU and driver, and saved five seconds after the last new pipeline and at the end. Shaders the game has shown before don't stall it the first time they appear in a run. (Lavapipe keeps nothing in it.)
- **Pipeline library** (v0.41.0): the driver's cache only holds what it compiled from the same SPIR-V, and the translators' SPIR-V changes from one version to the next, so after an update every shader stalled the game again the first time it appeared (a fight's start, a new scene behind a page turn). `pipeline_library.bin`, beside the cache, keeps what each pipeline was made from: its state (the renderer's pipeline key) and its shaders' sources, the vertex program (field by field) and the combiner setup, which the host keeps for each shader key it translates. At start a thread translates them all afresh and makes the pipelines, in the order they were first seen, while the game boots; a draw takes its pipeline from there (or waits if it's the one being made), and makes it itself only if it's new or the library's record of its shaders differs from the draw's (the record is then replaced and the file written again at the end). `QILIN_TRACE_PIPELINES=1` logs each pipeline a draw had to make and how long it took, and how many the library made ahead. A run that had to make none at draw time: 268 made ahead in 1.4 s on lavapipe.
- **Presenting** (v0.30.0) is a pass of its own: a triangle over the scaled rectangle samples the frame and looks each channel up in the gamma ramp (a 256×1 texture), into the window's image, black bars cleared around it. Where the window's images can't be drawn into, the scaled copy of v0.23.0 is the fallback, without the ramp. The game's ramp is each level i to about i × 254/255, nearly the identity. Since v0.30.2 the frame is scaled sharp bilinear: each window pixel samples at its own position pulled towards the nearest texel centre (by how many window pixels a texel covers, from the shader's derivatives), so texels stay solid blocks and only the window pixels across a texel edge blend; at whole-number scales that is nearest-neighbour.
- **Validation:** `QILIN_VK_VALIDATION=1` turns on the Khronos validation layer if it's installed. The renderer test runs with it in CI, on Mesa's software driver (llvmpipe) on Linux x64 and ARM64; it's skipped where there's no Vulkan device (the macOS and Windows runners).

## Aspect ratios (v0.37.0)

The game draws for a 4:3 or a 16:9 TV (the console's widescreen flag, which it reads into `[0x509703]` at start), always into its 640×480 frame: a 16:9 TV stretches the frame back out. Its cameras take their shape from a table of three film formats at `0x42A460`, each {aspect, film width, default focal length}: 4:3 {1.333, 15.54, 14.93}, 16:9 {1.778, 24.00, 23.05} and 2.35:1 {2.35, 24.00, 23.05} (the letterboxed cut scenes). A camera's horizontal field of view is 2·atan(film width / 2·focal length) (`0xF57F0`); its viewport is the display format's frame cut to its own format (`0xF56C0`, `0xF5760`), which is how the 4:3 comic pages are pillarboxed and the cut scenes letterboxed; the format in use is `[0x5077F8]`, set from the flag (`0x3321D`, `0x58252`), 0 for a moment around the comic pages.

Any other shape is the 16:9 format made wider or narrower (`host/aspect.cpp`): its aspect set to the new one and its film width scaled with it, so every camera keeps 16:9's vertical view and sees more (or less) at the sides; the focal lengths, and the cut scenes' 2.35:1 framing, stay as they are (at 21:9 they nearly fill the screen; wider, they're pillarboxed). 4:3 is the console's own 4:3 setting. The settings' `aspect` (auto, the screen's own shape, by default; 4:3 up to 4:1) is given to the game before it starts, and again between frames when the menu changes it: the flag, the 16:9 entry and the format in use are rewritten from the game's thread in `Swap`, so the frame it draws next is the first at the new shape and the window shows it at that shape. Auto follows the screen the window is on.

### The HUD (v0.39.0)

The game lays its 2D out in 640×480 and, for 16:9, lets the TV stretch it with the 3D. Its menus, comic pages and captions draw in a 4:3 viewport of their own (80,0 480×480 at 16:9), so they already have their shape; what it draws flat across the whole frame is the HUD in play (the heart and the count, through vertex program `040161A0`: four `dp4` of v0 with c0-c3, a constant colour) and, briefly, the "My Game" title over the menu's transition. A draw counts as flat when its program places its vertices by one matrix (its first four instructions `dp4 oPos.x … oPos.w, v0, c[n] … c[n+3]`, found once per program: `position_matrix_of`) and that matrix has no perspective (row w (0, 0, 0, k)); its extent across the screen comes from its positions on the CPU (the draws are quads, not in the vertex arena). On pictures wider than 4:3, a flat draw into a frame buffer across the whole frame's viewport, less than nine tenths of its width (so videos and fades stay as they are), is squeezed across by 4:3 over the picture's shape, back to its own proportions, about a point the vertex shader takes as a uniform (`kVsPixels` y and z: x becomes z + (x − z) · y, the identity otherwise, bit for bit): the screen's edge it's nearest (the settings' `hud = edges`, the default: a part within the left or right third keeps its distance from that edge in proportion; one in the middle third, its centre), the middle (`middle`: the whole HUD in the 4:3 area, as on a 4:3 TV), or none (`stretched`, as the game draws it). A part is the line it's on (v0.40.1): the flat draws of this frame and the last that share most of its height and sit within 3% of the frame's width of it, since the game draws a line of text in pieces (the pause menu's "Chapter 1, Scene 9: Basement" in three), which otherwise went three ways. At 4:3 nothing changes. Checked at 4:3, 16:9 and 21:9 in the mansion: the heart is round in its corner at each. The hearts and counts that float over characters are 3D sprites (vertex program `0401B010`, with perspective), so they stay with them.

## Render resolution (v0.38.0)

The renderer draws every frame buffer and render target at whole multiples of its size, across (`sx`) and down (`sy`), while the game sees its own sizes throughout (`Config::scale_x`, `scale_y`; `set_resolution_scale`). The settings' `resolution` gives `sy`, 1 (the original 480 lines) to 4 (1920), or auto: the height the picture is shown at in the window, rounded to the nearest multiple of 480; `sx` follows the picture's shape, round(`sy` × aspect × 3/4), so a wide picture, which stretches the game's 640 columns across it, gets as many more columns as it's wider (16:9 at 2×: 1920×960; 21:9 at 2×: 2560×960).

What the game gives in its own pixels is scaled on the way in: clear rectangles, scissors (the viewport is the whole image, so the clip-space positions the vertex programs produce land at the larger size unchanged), `CopyRects` regions, line widths, and point sizes (the vertex shader's size times `kVsPixels`, a uniform after the screen one). Reading a target back (a `BlockOnResource` hand-back, a frame-buffer lock, `--dump-frames`, the trace's dumps) gives it at the game's size, each pixel the average of the ones it became; writing one (a target seeded from guest memory, a CPU-written frame buffer) repeats each pixel. Changing the resolution while the game runs (the menu, or auto when the window changes size) makes every image again at the new size, the colour ones scaled into it and depth cleared (the game clears depth every frame), after the GPU is idle; the descriptor sets that named the old images are dropped. The present pass's sharp scaling snaps to the image's texels, not the game's (so the extra detail isn't thrown away), and the CRT's scanlines stay the game's 480.

Measured in the mansion at 16:9 (lavapipe): 2× is visibly sharper; validation, synchronisation validation included, reports nothing over the menus and a fight.

## FSR 1 (v0.38.0)

AMD FidelityFX Super Resolution 1 (`third_party/fsr1`, MIT) where the frame is shown larger than it's drawn and not at whole multiples (`Picture::fsr`, `sharpness`): EASU, edge-adaptive upscaling, from the frame to the size it's shown at, then RCAS, contrast-adaptive sharpening, at `sharpness` (0 to 1; 1 is RCAS's sharpest, each step down a fraction of a stop, 0 two stops), both compute passes (`gfx/fsr/fsr.comp`, 64 threads each covering four pixels of a 16×16 tile, as AMD's sample) into R8G8B8A8 storage images of the shown size, made again when that changes. The present pass then samples RCAS's output one to one, so the CRT look and the gamma ramp still apply. 32-bit floats throughout: 16-bit ones aren't everywhere (not the Raspberry Pi's V3D). The shaders are AMD's GLSL compiled once to SPIR-V by `tools/gen/fsr_spirv.sh` (glslang, checked by spirv-val) into `fsr_spirv.inc`, which is committed, so nothing compiles at build or run time; the constants come from AMD's own header built for the CPU (`fsr_constants.cpp`).

## SMAA (v0.39.0)

SMAA 1x (`third_party/smaa`, MIT) on the frame, at its own size (the render resolution), before FSR and the present pass (`Picture::smaa`, the settings' `antialiasing = smaa`): luma edge detection into an RGBA8 image (cleared; the pass discards where there's no edge), blending weights from the edges and SMAA's area and search tables (made as textures from its headers at first use; the search table sampled nearest), then neighbourhood blending into an image of the frame's format, which FSR or the present pass then reads in the frame's place. Each pass is a full-screen triangle with SMAA's own vertex and fragment code at the HIGH preset, every sample at level 0 (`smaa/smaa.glsl` over SMAA's custom-shader-language hooks), compiled once to SPIR-V by `tools/gen/smaa_spirv.sh` (`smaa_spirv.inc`, committed). Validation, synchronisation included, reports nothing with it on over the menus and a fight.

## Direct3D replacements so far

| Function | Replacement |
|---|---|
| `Direct3D_SetPushBufferSize` | Kept where the original keeps the values; there's no push buffer |
| `Direct3D_CreateDevice` | Reads the presentation parameters and starts the renderer. Makes the frame buffers (front plus back buffers) and the depth buffer as guest surfaces held by the device, with their pixels in contiguous memory, as the original does. The game asks for 640×480, one back buffer, D24S8 depth, no multisampling (`0x11` is `D3DMULTISAMPLE_NONE` on the Xbox, 1×1 samples) and presentation interval 2: 30 frames per second, as on the console. Any other multisample type stops the runtime |
| `D3DDevice_GetBackBuffer2`, `GetDepthStencilSurface2`, `GetRenderTarget2` | The surfaces, with a reference added. Index −1 is the front buffer |
| `D3DResource_Release`, `D3DResource_Register` | As the original (`AddRef` is lifted). A resource with no references left is destroyed by D3D's own `D3D_DestroyResource`, lifted (v0.21.0) |
| `D3DDevice_Release`, `D3DResource_IsBusy` (v0.30.1) | As the original: the device's count (`+0x934`) down by one (the last reference, which tears the device down at shutdown, stops the runtime); a resource is busy while the device holds it (an internal reference on it, or on a surface's texture), else its lock fence is cleared, the GPU never running behind here |
| `D3D_BlockOnResource`, `D3DVertexBuffer_Lock2` | See the lifted resource code above. A frame buffer is the exception (v0.30.0): the CPU locks it to read or write pixels, so its image is copied into guest memory first (CPU access to frame buffers, below) |
| `D3DDevice_CreateVertexShader` | Builds the original's shader object, and decodes the program (Vertex shaders, above) |
| `D3DDevice_SetVerticalBlankCallback` | Kept; called at each vblank (below) |
| `D3DDevice_SetGammaRamp` | Kept; frames written with `--dump-frames` go through it, as the TV would show them, and since v0.30.0 so does the window (Presenting, below) |
| `D3DDevice_BlockUntilIdle` | Waits for the GPU |
| `D3DDevice_Clear` | Colour, depth and stencil within the viewport, as the original (`0x176970`): each rectangle given clipped to the viewport, or with none, the viewport itself (since v0.36.0; before, the whole target, which broke the game's shadows: it draws every character's into a tile of one 256×256 texture and clears each tile through its viewport). Clearing some colour channels only stops the runtime |
| `D3DDevice_Swap` | Shows the frame, waits for the vblank the presentation interval asks for, runs the vblank callback (below), returns the swap count |

**Vblanks and the game's clock.** The game's vblank callback (`0xFC3B0`) counts vblanks, and on the one flagged `D3DVBLANK_SWAPDONE` records how many passed since the last frame: that count is the game's time step (`frame-timing.md`). So `Swap` does what the hardware did: it waits for the vblank the interval asks for, at the NTSC rate of 60/1.001 Hz, then calls the callback once for every vblank that went by, the last one flagged. A frame that takes too long gets a bigger time step, as on the console. Higher refresh rates come later (roadmap step 8).

**State setters and draws (v0.20.0).** Each setter stores what the original stores where the original keeps it (D3D's tables, the device's fields, dirty bits) and nothing else; the GPU methods the original would push are left to the renderer, which reads the state when it draws. Where the original derives guest-visible state with internal helpers (the default state, shader objects, a render target's depth range and multisample scale), the runtime calls those helpers, lifted. They write GPU methods as they go, into the device's push buffer: here a **sink** that nothing reads, which `MakeSpace` and `BeginStateBig` rewind.

## Drawing (v0.22.0)

Each draw call (and each `SET_BEGIN_END` pair the game pushes itself) becomes a renderer draw at once, in order with clears.

- **Vertices** are read from the shader object's attribute slots and D3D's stream table and converted to vec4 floats, attribute by attribute, as the NV2A reads its formats (D3DCOLOR's byte order, normalized shorts as (2s + 1) / 65535, the packed 11:11:10 format), missing components (0, 0, 0, 1). Quads, quad strips, fans, polygons and line loops become indexed lists (Vulkan has no quads, and Apple's Vulkan no fans).
- **Shaders are generated as SPIR-V** by the runtime's own builder (`gfx/spirv.*`), so nothing compiles shaders at build or run time. A vertex program comes from the GPU's program memory at the selected slot (`gfx/nv2a_vs.cpp`); registers are SSA values, as the program runs straight through. The program's screen-space output (D3D appends the viewport transform to every program) is mapped back to clip space with the target's size and depth scale, times w. The pixel side is the register combiners (`gfx/nv2a_ps.cpp`), keyed by everything in the shader definition but the constants, which are uniforms. Floats replace the hardware's 9-bit fixed point.
- **Derived state at draw time,** as D3D's state flush would push it: the viewport constants c-38 and c-37 (computed as D3D's `0x1710E0` does), blend, depth, stencil, cull and colour-write state from the render states, the combiner constants.
- **Textures** (`gfx/texture.*`): swizzled, linear and DXT1/3/5, every level, face and slice, decoded to RGBA8 and cached; once a frame each texture drawn with is compared byte for byte with a copy of the texels it was made from (since v0.31.0; a hash before), and re-uploaded when they differ. Linear textures are addressed in texels, as the hardware does.
  - **DXT on the GPU** (v0.32.0): DXT1, DXT3 and DXT5 are BC1, BC2 and BC3, the same 4×4 blocks decoded by the same rules (DXT1's three-colour mode with transparent black, as BC1_RGBA; DXT3 and 5 always four colours). Where the device samples BC1-3 with filtering (`textureCompressionBC`: desktop GPUs, Apple's, lavapipe; not the Raspberry Pi's V3D), the guest's blocks go to the GPU as they are, a quarter (DXT1) or an eighth of the memory, with no decoding on the game's thread; elsewhere, and for volume textures, they're decoded as before. The guest stores them in rows, not swizzled, each face's levels back to back (a level under 4×4 is one block), cube faces padded to 128 bytes. `qilin_gfx_tests` draws each format both ways: the GPU's texels are within 2 levels of the decoder's (the GPU rounds the interpolated thirds and fifths its own way; the NV2A's rounding isn't known either). `QILIN_NO_BC=1` decodes them on the CPU. The attract sequence and menus upload 339 DXT textures in their first 90 seconds, 10.6 MB as blocks.
  - **Changed texels into the image they have** (v0.32.0): a texture whose texels change (a video frame written every frame: about 720 MB of re-uploads in the first 90 seconds) is written into its existing image, after a barrier on the draws that sampled it, instead of a new image made and the old one destroyed. Texels go through the vertex ring (host-visible, already mapped) rather than a buffer and memory allocation of their own each time; only uploads larger than half the ring get their own.
- **The fixed-function vertex pipeline** (v0.24.0) is generated as an NV2A vertex program, which the same translator makes SPIR-V: the position through World × View × Projection (the device's matrices, as `SetTransform` keeps them), then the screen-space transform D3D appends to programs; the diffuse and specular colours and the texture coordinates passed through. What the game uses so far is untransformed positions with or without a diffuse colour (FVF `0x42`, the menus; `0x2`, in play), a vertex without one taking the attribute register's (white, as `SetVertexShader` leaves it). While `SetModelView`'s flag is on, the title's own composite stands in for World × View × Projection: it already includes the viewport (as D3D's own does, from `GetProjectionViewportMatrix`), so the screen-space step only divides by w. `DrawVerticesUP` (v0.28.0) reads each attribute at its slot's offset in the caller's vertices, as the original copies them inline, after the flush it makes (dirty flags `& 0xC0000070`, then `0x20` becomes `0x50`). Vertex blending, texture-coordinate generation and remapping and texture transforms stop the runtime until they're modelled. Lighting does too, but can't be reached: the XBE has no `SetLight` or `SetMaterial` (the linker kept only what the game calls), so the game lights everything in its own vertex programs. Fog (v0.30.0) sets the vertices' fog coordinate as the original sets the fog unit's source: the specular alpha without a table mode, else the eye-space z (planar), or the distance to the eye with `D3DRS_RANGEFOGENABLE` (radial), from the model-view in c4-c7.
- **Pre-transformed (XYZRHW) vertices** (v0.27.0) run the original's own passthrough program, as its state flush (`0x173900`) loads it: one of three NV2A programs in the image, chosen by the fog table mode (`0x17FC28` without one; with one, `0x17FB78` or `0x17FAB8` by the device's flag 2), translated like the game's programs. They scale by `c-96` (the multisample scale, the depth scale, and the w scale: the depth scale times the device's `+0x940` with w-buffering, else 1) and offset by `c-95` (the screen-space offset, less half a pixel where the original takes it), which the runtime loads as the original does, into the GPU's constants, where they stay. The program writes fog from w, z or the specular alpha.
- **The fixed-function pixel pipeline** (v0.24.0): D3D's texture-stage operations as register-combiner settings, as the original's state flush makes them: a general combiner stage per texture stage up to the first one disabled, "current" in r0 (the diffuse colour at stage 0), "temp" in r1, the texture factor in each stage's C0, the final combiner passing r0 through. Select, modulate (1×, 2×, 4×) and add, with complemented and alpha-replicated arguments; other operations and result arguments stop the runtime. The final combiner (v0.30.0) is the original's (`0x178AC0`): with fog the colour is fog.a × r0 + (1 − fog.a) × the fog colour, the specular colour added with `D3DRS_SPECULARENABLE`; without fog, r0 (plus the specular).
- **Fog** (v0.30.0), as the original's state flush (`0x178AC0`) programs the NV2A's fog unit from the render states: off; linear on the vertices' own fog value with parameters (1, 1) without a table mode; linear from `D3DRS_FOGSTART` and `FOGEND` (P0 = end·s + 1, P1 = −s, s = 1 / (end − start), or the image's 8192 when they're equal); exp and exp2 from `D3DRS_FOGDENSITY` times the constants the image holds (`0x203734`, `0x203730`). The fragment shader computes the factor per pixel from the interpolated fog coordinate as the hardware's formulas have it (linear P0 + P1·c − 1; exp P0 + 2^(16·P1·c) − 1.5; exp2 P0 + 2^(−32·(P1·c)²) − 1.5), clamped, into the fog register's alpha, with the fog colour in its rgb.
- **Depth from a texture** (v0.29.0): texture modes DOTPRODUCT (stage 2) and DOT_ZW (stage 3), `texm3x2depth` on the Xbox. Each dots its own (s, t, r) with an earlier stage's texel (`PS_INPUTTEXTURE`), read as a vector by the stage's `PS_DOTMAPPING`: as is, the three signed byte encodings (D3D's, OpenGL's, two's complement), or HILO_1, the texel's 32 bits as two 16-bit halves (hi: alpha and red, lo: green and blue) and 1. Both registers read zero; the pixel's depth becomes stage 2's product over stage 3's, clamped to [0, 1] (the fragment shader writes `FragDepth`). The game reads the depth surface of a 640×480 scene it renders into a texture this way, as an A8R8G8B8 texture, and writes that depth into the depth and stencil buffer (below: depth surfaces read as textures).
- **The other texture modes** (v0.30.0), in the arrangements the NV2A allows, each reading an earlier stage's texel: **BUMPENVMAP** and **BUMPENVMAP_LUM** (`texbem`, `texbeml`): the earlier texel's blue and green as signed (du, dv), through the stage's 2×2 bump matrix, added to (s, t) for the stage's lookup; _LUM scales the colour by the texel's red times the luminance scale plus its offset, clamped. The matrix and luminance terms come from the texture-stage table entries D3D pushed them for (`SetTextureState_BumpEnv`, `0x1719D0`: the stage itself under a pixel shader, the one before for the fixed-function stages), the matrix in the order D3D pushes it. **DPNDNT_AR** and **DPNDNT_GB**: the earlier texel's (alpha, red) or (green, blue) as coordinates. **DOT_ST** (stage 2 after DOTPRODUCT): the two dot products as (s, t). **DOT_STR_3D**, **DOT_STR_CUBE** (stage 3 after two dot products): the three as (s, t, r) into a 3D or cube texture. **DOT_RFLCT_DIFF** (stage 2) and **DOT_RFLCT_SPEC** (stage 3): the three dot products as a normal n into a cube map, the specular stage reflecting the eye vector e (the three stages' q) about it, 2·n·(n·e)/(n·n) − e. DOT_ZW also at stage 2. **The HILO hemisphere mappings**: the two 16-bit halves signed (D3D's /32767, OpenGL's (2v + 1)/65535, or /32768), the third component √(1 − x² − y²). BRDF and DOT_RFLCT_SPEC_CONST stop the runtime (the hardware's eye-vector register isn't kept). The bump-map formats decode too: V8U8 (G8B8), L6V5U5 (R6G5B5, its 5-bit U and V as signed bytes of the same value) and R8B8. `qilin_gfx_tests` builds every mode with every dot mapping and checks the SPIR-V.
- **Palettized textures** (v0.30.0, format P8): each texel an index into the stage's palette, the device's `D3DPalette` at `+0xF88` + 4·stage (`SetPalette`): its size from the header's `Common` bits 30-31 (256, 128, 64 or 32 entries), A8R8G8B8 entries from its data. The texture is decoded through the palette and cached with it, so a palette change re-decodes it.
- **Points and point sprites** (v0.30.0): every vertex shader writes a point size: a program's `oPts.x` where it writes it, else `D3DRS_POINTSIZE`; the fixed-function program computes it as the NV2A's point parameters do (`LazySetPointParams`, `0x1783E0`): `D3DRS_POINTSIZE` in pixels, or with `D3DRS_POINTSCALEENABLE` the viewport height × the size × 1/√(A + B·d + C·d²) from `POINTSCALE_A`-`C` and the distance to the eye. The size is clamped to `POINTSIZE_MIN` and `_MAX` and to the hardware's 63.875 pixels (the device's `largePoints` feature is turned on where there is one). With `D3DRS_POINTSPRITEENABLE` a point list's stages 0-2 take the position within the point, (0, 0) at its top left to (1, 1), as their texture coordinates; stage 3 keeps its own (as xemu has it; not checked against the hardware).
- **Culling:** D3D's cull modes name the winding culled as it appears on screen: `D3DCULL_CW` culls clockwise triangles, `D3DCULL_CCW` counter-clockwise ones. (v0.22.0 to v0.25.0 had it the other way round, reasoned from the GPU methods; the attract sequence's books showed it wrong: pages read mirrored and the desk behind them was culled away.)
- **Rendering into textures** (v0.26.0): when the render target is a texture's surface, draws and clears go to a renderer image for it (B8G8R8A8, made the first time, by the guest address of its texels), with the device's depth buffer when the game pairs them and the sizes match. A texture whose texels were last drawn by the GPU is sampled from that image directly: nothing is read back to guest memory. Guest memory keeps what the CPU last wrote there, hashed when the target is drawn (since v0.31.0, only the first time in a frame and after a lock, a destroy or a `CopyRects`, the ways D3D lets the CPU at a resource: a 640×480 target is 1.2 MB, and hashing it at every draw was most of a draw's cost); if it changes (a CPU write, or the memory reused for another resource), the guest's texels take over again. The game renders a 256×256 texture every frame from early in the attract sequence, and whole scenes at 640×480 with depth for the comic-strip pages. Since v0.29.0 a texture target can have its own depth surface (D24S8, swizzled or linear, at least the target's size): the renderer makes a depth buffer for it the first time, by the guest address of its data, cleared to zero; what it holds isn't in guest memory. The game draws a 640×480 scene into a texture with its own depth buffer in play. Since v0.30.1 a render target's image starts from the texture's memory (on the Xbox the GPU draws over it), and takes what the CPU wrote since the GPU last drew. Drawing into the front buffer, other formats and sampling the texture being drawn into stop the runtime.

- **Depth surfaces read as textures** (v0.39.1): a texture target's depth surface lives only on the GPU, but the game also samples its memory as a linear A8R8G8B8 texture. When an imp dies, it renders the imp into a 640×480 texture (`03634000`) with its own depth surface (`03508000`), then draws a quad (vertex program `040129E0`, colour writes off) that reads that surface through DOTPRODUCT and DOT_ZW, so the imp's depth meets the scene's: the stencil becomes 0 where the imp is in front, 1 elsewhere (ALWAYS, ref 1, depth-fail REPLACE, pass ZERO). The goo is then drawn over the quad (`04012D10`, stencil EQUAL 0), opaque throughout, so the stencil alone gives it the imp's shape. Such a read now gets the depth target's depth and stencil packed into a colour image as the console's memory holds a D24S8 word (alpha, red and green the depth's bytes from the top, the range 0 to 1 as 0 to 0xFFFFFF; blue the stencil: `Renderer::pack_depth`, a full-screen pass over the depth and stencil aspects, `gfx/depth/depth_pack.glsl`, compiled once by `tools/gen/depth_pack_spirv.sh`), made again after the surface is next drawn into (`depth_texture` in `d3d.cpp`). Where a device can't sample its depth format, the memory is read as before. The handover between the two uses of one block of memory goes both ways: the game first copies page turns into the memory it later reuses for this depth surface, and that copy's image used to stay attached to the address, since neither the GPU's depth writes nor the CPU touched the memory that's checked; so the effect read an old screenshot as depth, and the stencil came out as whatever that picture made it, from a box around the imp to goo over the whole screen. Now a block of memory bound as a depth surface drops a colour image kept for it, and one made a colour target drops a depth target. With that, the quad's own pixel shader decides the rest: it outputs t0 under the game's alpha test (> 5), with stage 0 NONE; a NONE stage reads (0, 0, 0, 1) (`nv2a_ps.cpp`: inferred from this effect, which only works if those pixels pass; NV_texture_shader and xemu have zero; every other shader the game was seen to run overwrites what it would read of it). `qilin_gfx_tests` packs a depth target cleared to known depths and stencils and checks the words.

- **CPU access to frame buffers** (v0.30.0): `D3D_BlockOnResource` on a frame buffer, which D3D calls before the CPU locks one, copies the renderer's image into the surface's guest memory and records a hash of it. The next draw, clear, `Swap`, or the host's housekeeping while the game waits (every 16 ms), compares: memory the CPU changed goes back up to the renderer's image, and a changed front buffer is shown at once. The disc-error screen draws its message into the front buffer this way and loops without swapping; it now shows. The watch ends at the next `Swap`.

**Depth bias and line width** (v0.33.4; v0.43.3: a biased draw with depth writes off gets 8× the constant offset, `kOverlayBias`, as the shadows striped on NVIDIA at every setting): `D3DRS_ZBIAS` is the polygon offset the original's `SetRenderState_ZBias` (0x171660) programs, factor −ZBias × 0.25 and units −ZBias, as Vulkan's depth bias (slope and constant factors). The game's projected shadows (each character's silhouette rendered into a 256×256 texture, then sampled PROJECT2D onto the floor, one character after another) use a bias of 4 and a less-or-equal test: the floor drawn again by another vertex program, only where its depth meets the floor's own. That only works when the two programs compute the same depth, as the NV2A's do: since v0.37.0 every translated vertex program computes with `NoContraction` on its arithmetic and an `Invariant` position, so a GPU's compiler can't fuse or reorder the two programs differently (on real GPUs the shadows otherwise fell behind the floor in patches: flickering while characters move, missing in some poses). Two more things made the depths differ by GPU (v0.41.0): OpDot, whose order of products and sums (and fusing) is each GPU's own, and the reciprocal (`rcp`/`rcc`, which the programs use for the perspective divide), which Vulkan allows 2.5 ULP out. Dot products are now products and sums in a fixed order, each rounded as IEEE has it, and the reciprocal is refined by one Newton step to within about one ULP. And the slope factor is per pixel: at a render resolution s times the game's, the depth changes 1/s as much from pixel to pixel, so the console's offset needs the factor times s (the larger of the two axes' multiples, so it's never less than the console's). Measured on lavapipe by drawing the shadows solid black and counting their pixels against the same draws with no depth test: the bias passed 97.5% of them before (the rest in patches along the floor), all of them after, within the frame-to-frame noise. Dying imps get a 64×64 target of their own, rendered once from above and projected onto the floor while their bodies fade. `D3DRS_LINEWIDTH` (`SetRenderState_LineWidth`, 0x171570: the width times the supersampling scale, in eighths of a pixel up to 63.875) is Vulkan's line width where the device has `wideLines`; the game draws lines 14 pixels wide. An audit of every render state and texture-stage state the draw path doesn't read, over the intro, the menus and play, found the rest at D3D's defaults: shade mode, the polygon-offset enables, the material sources, fill modes, front face, alpha kill, colour keys, texture transform flags, maximum anisotropy. The multisample modes change, but only set the console's supersampling.

**Not modelled yet:** most of the fixed-function pipelines (above), BRDF and DOT_RFLCT_SPEC_CONST, the parametric details the hardware has that floats don't (the combiners' fixed-point precision), a CPU read of a texture the GPU rendered other than through `CopyRects` (its guest memory holds what the CPU last wrote), draws from `SetVertexShaderInput` streams, `Swap` keeping a render target that isn't the back buffer.

## Tracing draws (v0.37.0)

`QILIN_TRACE_DRAWS=N[,M]` logs every clear, draw and copy of frames N to M on stderr, one line each: the render target and depth surface, the viewport, the primitive and vertex count, the program kind, the textures (address and format), blending, depth, stencil, ZBias, colour writes, the alpha test, culling, the texture modes, the first combiner stage and the vertex shader; also when a render target is handed back to guest memory, seeded from it, or dropped. `QILIN_TRACE_MATCH=a|b` keeps only the lines containing one of the strings. `QILIN_TRACE_DETAIL=1` adds, under each logged draw, its stencil and alpha-test state, every combiner stage (inputs, outputs and constants), the final combiner, the texture modes, and its first four vertices' attributes; clears show the stencil value too (`s=`), and the trace notes depth surfaces packed and colour or depth images dropped when their memory changes use. `QILIN_TRACE_DUMP=dir` writes the frames with a logged line there (`frame_NNNNN.png`) and what each render target a logged draw samples holds at that moment (`swap_n_address.pam`). The green boxes in v0.39.1 were found with it: frames dumped while the effect drew, the box's frames found by their colour, the render targets they sampled read from the dumps. The shadow investigation in v0.37.0 used it to check the silhouettes each projection samples and the tiles dying imps get.

## Captures (v0.42.0)

F9 starts a capture: for the next 12 frames the draw trace runs with every detail, into `trace.txt`, with each frame as shown (`frame_NNNNN.png`, at the game's size) and each render target a draw samples as it is at that moment (`swap_n_address.pam`, written once for each state of the target: the shadows' 256×256 target is drawn and sampled once per character), all packed into `captures/<date-time>.tar` in the data folder (a ustar archive; the game shows the path for a few seconds and logs it). The header names the version, the GPU and the picture settings. It's for faults that only show on a GPU this was never run on: the player presses F9 while it shows. A draw numbered N is in the frame numbered N + 1. The first frame has every draw as one line; the others only the draws that draw into a texture, sample one the game draws into, or have a depth bias, each with its details and the vertex program's constants c0-c11 and the viewport's (a whole frame's details are 4 MB). **A test run** (v0.42.1): `selftest.txt` in the data folder, read at the first frame and renamed `selftest.ran`, has lines of `SECONDS key NAME [held SECONDS]` (SDL's key names, held as if on the keyboard: `platform::hold_key`), `SECONDS capture` and `SECONDS quit`; it plays the game on a machine nobody is at the controls of, so a build can be tried on a player's GPU and its log and captures read afterwards. Such a run has a hard disk of its own (`selftest-disk` in the data folder, emptied each time: v0.43.0), so it starts a new game the same way every time and leaves the player's saves alone. The first frames of a capture are also written at the render resolution (`full_NNNNN.png`, v0.43.4: `read_front_buffer_full`), as the reduced frames average thin stripes away. **The game's step is held through a capture** (v0.43.0): a captured frame takes hundreds of milliseconds (read back, written out), which the game's clock would turn into its longest step (1/12 s); it gets the step it had before the capture instead (`g_capture_holds_step` in `frame_clock`), so twelve frames at 144 Hz are twelve consecutive 144 Hz frames.

**Comparing what hasn't changed** (v0.43.1; off since v0.43.2 unless `QILIN_QUICK_COMPARE=1`, after a player saw a fault picking items up that began with it: whole comparisons once a frame and after any lock, as before, until what it missed is found). The renderer draws from copies of guest memory (converted vertex runs in the arena, textures as images), and each copy is checked against the memory it came from before it's used. Until v0.43.1 that was a whole comparison of every run and texture at its first use in a frame, and again after any vertex buffer lock (one count, `memory_epoch`, for everything): 12 MB of vertices a frame in the first fight, 13.5% of the game thread in `memcmp`. Now locks are counted per resource (`Device::vertex_locked`: the data address locked, and the count at its last lock; a run belongs to the locked buffer nearest at or below it, a texture to locks that start within its texels), so a lock has only that resource's copies compared again. And memory still for `kSettledSwaps` (60) frames is compared whole only after such a lock and one frame in sixteen (each copy on its own frame, `quick_look`); the other frames compare eight words spread over it (`sample_bytes`). A scene loaded over the same memory, with no lock, fails that at once; a lock-less write that misses all eight words would be seen up to fifteen frames late. `QILIN_CHECK_SETTLED=1` makes the whole comparison too and reports what the quick look missed or what changed between two draws of one frame: none through the story and the first fight. `QILIN_VERTEX_STATS=1` logs, every 600 frames, how many runs were seen already, looked at quickly, compared whole or new, with their megabytes. The same frames then compare 2.3 MB whole, and the game thread's samples over the same 56 s of fight fall by 14%.

**Textures' memory** (v0.43.0): a texture's image is bound to a piece of a 16 MB block of device memory (`texture_blocks_`: first fit at the image's alignment, pieces merged back as textures are destroyed, an empty block returned unless it's the last of its memory type), not to an allocation of its own. A driver allocation per texture was most of the 0.3-0.4 ms a new texture cost on Windows (NVIDIA), and a scene's textures arrive together: 35 in the frame the first fight began. A texture over a quarter block, or when no block can be had, gets its own memory as before; render targets always do.

**Long frames** (v0.41.2, finer in v0.42.0) go to the log: every frame over 50 ms, and frames over 10 ms that took two and a half times the running average (at most 40 a second, 2000 a run), each with the game's share (and within it file reads, pipelines made for draws, textures made or written) and presenting's. `QILIN_NO_DRAW=1` skips every draw (clears and presents stay), which lets a software renderer reach 150 frames a second headless: how the sound and the game's logic are tried at a fast machine's rates.
