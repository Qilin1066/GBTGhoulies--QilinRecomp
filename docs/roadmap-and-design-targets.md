# Grabbed by the Ghoulies — Recomp Roadmap & Design Targets

**Guiding principle: efficiency and reliability come first.** Every design choice is judged on whether it makes the game cheaper to run on low-end hardware and whether it fails loudly and predictably instead of silently misbehaving.

## Targets
- **Platforms:** 64-bit Windows, Linux and macOS (Intel and Apple Silicon), on x86-64 or ARM64, with Vulkan. See *Hardware scope* below.
- **Language:** **C++23** throughout (recompiler, generated code and runtime). Minimum compilers: GCC 14, Clang 19, Xcode 16, Visual Studio 2022 17.10. No DirectX anywhere.
- **Graphics API:** **Vulkan 1.3, and only Vulkan.** We require the 1.3 core API, and only the optional features and limits that Mesa's v3dv driver on a Pi 4 provides, so one render path works everywhere (MoltenVK on macOS). See *Vulkan baseline* below.
- **Reference:** xemu running the original game is ground truth for behaviour and visuals. The existing Windows-only Ghoulies PC Recomp (xboxrecomp-based, D3D11) is a second behavioural reference; its known-issue list doubles as a regression checklist (see `prior-art.md`).
- **Enhancement example target:** 3440×1440 (21:9) at 144 Hz.

## Architecture
- **Game code:** static recompilation, x86 → **generated C++**, compiled AOT by clang/MSVC for each target. No interpreter, no JIT. Hand-written C++ replaces lifted functions over time (hot paths, bugs, enhancement hooks) through a function override table.
- **Decoder:** **Zydis** (MIT, proven in XboxXBERecomp), vendored into the repo, and **verified instruction by instruction against LLVM's disassembler across the whole binary** in CI. Own decoder only as a fallback. (Revised after prior-art review; see `prior-art.md`.)
- **XDK symbol naming:** XbSymbolDatabase (MIT, Cxbx-Reloaded's OOVPA signatures) to name D3D8/DSOUND/XAPI/CRT functions; own masked-hash signatures only where it lacks XDK 5659 entries.
- **Register model:** guest registers held in host locals inside each lifted function and synced to a context struct only at call/indirect boundaries. No global or thread-local register variables (that model blocks host register allocation).
- **Calling conventions:** the game is VC++ 7-era LTCG code with custom register conventions (e.g. `eax` argument at `0x1DF70`). Lifted code keeps full register state across calls; ABI recovery only where hand-written C++ replaces a function.
- **Fail loudly:** an undecodable or unsupported instruction is a build error, never a comment; an unknown indirect-call target at runtime traps with its address logged.
- **Control flow:** recursive-descent CFG with resolved switch tables (done in analysis tooling, ported to the C++ recompiler). Indirect calls dispatch through a generated sorted function table; an unknown target traps with the address logged (never silently continues), and the address is added as a seed.
- **Lifter efficiency:** flag elimination via dataflow analysis (compute only flags that are read); scalar SSE → native `float` (bit-exact on ARM); x87 → native `double`, honouring the game's x87 precision-control setting (24-bit, exact; done in slice 3), with transcendentals from a bundled implementation, correctly rounded and the same on every host (done in v0.9.0); flat memory (4 GB host reservation, `base + addr`, no bounds checks). Both platforms are little-endian.
- **Memory mirrors:** the Xbox maps RAM at several aliases (xboxrecomp needs 28 mirror views). ✅ Learned in bring-up (v0.16.0): the game uses two, both through D3D's lifted resource code: `0x80000000` (contiguous memory) and `0xF0000000` (the write-combined window surface locks return). Guest RAM is one shared-memory object mapped at 0 and at those two, inside one 4 GB host reservation (memfd / shm / Windows placeholder views); any other address outside RAM isn't mapped, and an access there stops the runtime naming the address (a fault handler; `QILIN_CHECKED_MEMORY` checks each access instead).
- **Exceptions:** explicit frame chain. 20 game functions link C++ EH records into `fs:[0]`; lifted code keeps that chain in guest memory exactly as the original does (each guest thread has its own TIB). Nothing in the game handles an exception it can throw (they're STL `logic_error`s, and the only resuming `catch` guards an allocation that never throws), so the runtime's `_CxxThrowException` stops with the exception's type and message instead of unwinding (decided in v0.7.0; see `recompiler-core.md`).
- **Kernel + XDK libraries:** the kernel and the libraries that drive hardware (D3D8, DSOUND, XPP) are replaced with native C++ implementations, not recompiled. Library boundaries are known (see `code-analysis.md`). Libraries that are pure computation over an interface we replace are lifted instead, the functions lifted code reaches: the C runtime (v0.11.0), XAPI (v0.12.0), XACT and XGraphics (v0.15.0). Exact `printf` formatting, x87 maths, heap behaviour, XGraphics maths and XACT's cue logic matter more than native speed, and the interfaces beneath them (the kernel, DirectSound, D3D) are narrower and documented. Hot, simple functions can still get native versions, each checked against the lifted original.
- **Graphics:** D3D8 API-level translation to Vulkan, not NV2A emulation. **Plus a minimal NV2A command interpreter for `BeginPush`/`EndPush`**: the game writes raw `SET_BEGIN_END` + `INLINE_ARRAY` immediate-mode draws in 17 functions; these become `DrawPrimitiveUP`-equivalents with the current vertex format. Unknown methods assert. Shaders/combiners converted to SPIR-V offline; prebuilt pipeline cache (no runtime compile stutter).
- **Video:** Bink 1 movies decoded with FFmpeg (libavcodec), uploaded as Vulkan textures.
- **Audio/Input:** XACT lifted (v0.15.0); DirectSound → native voices and mixer (`audio.md`), output on SDL3; WMA through the XBE's own decoder, lifted (v0.30.0); controller → SDL3 (Xbox One pad over Bluetooth is the test controller).
- **Assets:** `.bnl` bundles are zlib streams → system zlib (replaces the zlib copy inside the game).
- **Threads:** ✅ audio mixing on its own thread, the GPU one submission behind the CPU (v0.30.0); guest threads on host threads with the Xbox's single-processor scheduling.
- **Portability rules:** no inline asm or x86 intrinsics in the runtime; ARM64 Linux builds from day one.

## Hardware scope
**Supported: 64-bit hosts with a Vulkan 1.3 driver.** In practice that means:
- **Windows and Linux** on x86-64 or ARM64 with a Vulkan-capable GPU and driver;
- **macOS on Intel and Apple Silicon Macs**, through MoltenVK (Vulkan on top of Metal): any 64-bit Mac with a Metal GPU running macOS 10.15 (Catalina) or later: officially the 2012 and later Intel models, and every Apple Silicon Mac. MoltenVK has Vulkan 1.3 from v1.3.0, and its releases up to v1.4.1 still run on 10.15 (v1.4.2 raised the floor to 12), so Macs on 10.15–11 get one of those. The runtime (what players run) is built for macOS 10.15, and CI builds both architectures. It doesn't use `std::format`, which Apple's libc++ only has from macOS 13.3; it formats with `qilin::strf` (printf-style). The developer tools (`qilin`, the tests) use `std::format` and need macOS 13.3;
- **ARM boards** with Vulkan 1.3 drivers, e.g. Raspberry Pi 4 and newer (Mesa v3dv, Mesa 24.3 or later).

**Out of scope:** anything without Vulkan 1.3 (or, on Apple, a Vulkan translation layer that provides it), and 32-bit hosts. That rules out the Raspberry Pi 1–3 and Zero (OpenGL ES 2 only), the first Intel Macs (32-bit Core Duo, 2006), and Macs without a Metal GPU or that can't run macOS 10.15. Because of this there is one renderer (Vulkan) and one memory model: the Xbox's 4 GB address space mapped flat into a 64-bit host's address space, with no windowing cost on memory accesses.

### Vulkan baseline: 1.3
The renderer targets **Vulkan 1.3** as its minimum API version, chosen for how widely it's supported:
- **Raspberry Pi 4 and 5:** Mesa's v3dv driver is Vulkan 1.3 conformant from Mesa 24.3.
- **macOS:** MoltenVK supports Vulkan 1.3 from v1.3.0, on Intel and Apple GPUs alike. Older Intel GPUs may lack some of the v3dv feature set; the start-up check names what's missing.
- **Windows and Linux:** current desktop GPU drivers (AMD, Intel, NVIDIA, Mesa) all ship 1.3.

1.3 makes several things core that would otherwise be extensions to probe for, and the renderer is designed around them:
- **Dynamic rendering:** no render pass or framebuffer objects. That suits D3D8's free-form render-target switching.
- **Synchronization2:** simpler, less error-prone barriers.
- **Extended dynamic state:** cull mode, depth test and write, compare op, topology and stencil can be set per draw. That cuts down how many pipelines D3D8's render states need, which matters for the prebuilt pipeline cache.
- **Timeline semaphores** (core since 1.2): CPU–GPU pacing for frame timing.
- **Others:** `maintenance4`, inline uniform blocks, and pipeline creation cache control.

1.3 core is the floor, but optional features and device limits aren't: v3dv is the reference for those. The renderer checks the features it uses at startup and fails with a clear message if one is missing, rather than taking a fallback path. Nothing beyond 1.3 core and the v3dv feature set is used without a decision recorded here. Vulkan 1.4 is out of scope for the baseline.

**Low-end reference:** a Raspberry Pi 4–class board is our reference for typical low-end hardware. It's what we measure efficiency against and test on. It is not a floor: anything with Vulkan 1.3 that's slower is fair game if the efficiency work gets us there. The Vulkan feature set we use is kept small (1.3 core, plus what v3dv on a Pi 4 supports) so the one render path runs on all of it.

## Settings, not platform branches
All enhancements live behind a settings file with presets, e.g.:
- *Low-end:* 1× resolution, no AF, no MSAA, original aspect and frame rate.
- *Desktop:* scaled resolution, 16× AF, MSAA, widescreen, interpolated high refresh rate.

See `recompiler-core.md`.
3. **Runtime skeleton:** 🔨 in progress (`runtime.md`). ✅ `qilin_run` loads the XBE into 64 MB of guest RAM, sets up the stack, thread information block and kernel imports, and calls the lifted `main`; ✅ replacement registry that stops on anything unregistered, naming it and its caller; ✅ guest heap; ✅ first XAPI replacements; ✅ the C runtime and XAPI lifted, start-up run as XAPI ran it; ✅ kernel: critical sections, virtual and contiguous memory, timers and DPCs (recorded), console settings; ✅ guest RAM size a setting (64 MB default); ✅ the file system over the extracted disc and a data folder; ✅ XDK library functions named by signature (XbSymbolDatabase); ✅ XACT and XGraphics lifted, DirectSound native over a software mixer (`audio.md`). ✅ the scheduler: guest threads on host threads, waits, timers, DPCs (v0.30.0). To do: the rest of the 81 kernel imports, and the 167 library entry points lifted code calls directly (D3D, XACT, DSOUND …; `_CxxThrowException` stops with a diagnostic).
4. **Boot to first frame:** 🔨 in progress (`graphics.md`). ✅ Vulkan 1.3 renderer (clears, frame flips, read-back; tested in CI on Mesa's software driver with validation); ✅ the Direct3D device, frame buffers, `Clear`, `Swap` at the display's vblank with the game's vblank callback. ✅ audio start-up. ✅ textures, surfaces and vertex buffers created (D3D's resource code lifted). To do: shaders and drawing (next), a window on SDL3.
5. **Playable at original spec:** 640×480, 4:3, original frame rate; matches xemu; tested on low-end reference hardware at every milestone.
6. **Resolution / AF / MSAA:** scaled render targets (decide per render-to-texture target), HUD half-pixel fixups, CPU framebuffer readback handling.
7. **Widescreen 16:9 → 21:9:** patch the projection (Hor+), widen the culling frustum, re-anchor the HUD, pillarbox 2D/FMV, per-scene aspect caps where the extra view reveals unfinished geometry.
8. **High refresh rate:** ✅ investigated (`frame-timing.md`). ✅ v0.40.0: the frame clock replaced natively, 30 / 60 / the display's rate / unlimited, low-latency pacing, the transition timers that stalled at a short step fixed. The game is variable-timestep by design (dt = vblanks since last present / 60, clamped to 5 frames, plus a 300 Hz tick accumulator, computed in `0xFC030`). Plan: override `0xFC030` to feed real elapsed time, replace the busy-wait loops (`0x32680`/`0x32700`) with sleeps, pace frames from the Vulkan swapchain. Playtest 30/60/144/240 Hz against xemu; optional fixed-step + interpolation mode kept only as a fallback for systems that assume dt ≥ 1/60.
9. **Extras:** texture replacement packs (hash on upload), etc.
